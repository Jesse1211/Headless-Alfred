# v0.4 Tool-Lifecycle Transparency Design

**Date:** 2026-06-17
**Status:** Pending review (revised after feasibility audit)
**Predecessors:** [`2026-06-13-claude-ui-mode-design.md`](2026-06-13-claude-ui-mode-design.md), [`2026-06-15-summary-template-design.md`](2026-06-15-summary-template-design.md)

## Problem

When a Claude turn dispatches a `Monitor` tool (long-running
background polling) or an `Agent` subagent (synchronous tool with no
intermediate progress visible to the parent), the user can see
neither what was dispatched nor how it's progressing. Concrete pain
in production (oracle pod, jsonl forensics 2026-06-17):

- The user sent prompts like "检查的如何 / 咋样了? / 你一直运行一直检查"
  every 5–15 minutes during a long CI run. They were manually
  polling Claude because the UI gave them nothing else to look at.
- 11 Monitor tools were dispatched across that session. The UI
  showed them as identical "Monitor" rows with a status chip; user
  had no way to tell which polled which CI workflow or how long
  any had been running.
- 11 Agent subagents were dispatched. Each looked like a single
  inert spinner for 2+ minutes; subagent's own progress was
  completely invisible.

A separate confusion was suspected — that the "another prompt is
still in flight" rejection fires after `result` because the CLI is
still draining background task notifications. **Forensics ruled
this out**: alfred releases its `runStates` slot the moment the
`result` event arrives ([`claude_handlers.go:524`](../../../internal/api/claude_handlers.go)),
and the jsonl shows zero cases where the user's next prompt fired
faster than that release. So this design does NOT introduce a new
"session_idle" gating signal — none is needed.

## Goal

Make the in-flight state of every tool, subagent, and background
Monitor task visible in the UI, so the user can:

- See which subagents are currently running and what they were
  asked to do.
- See which Monitor tasks were dispatched, with their description.
- See how long each tool has been running, with visual escalation
  when something runs unusually long.
- See at a glance what phase the current turn is in
  (Initializing / Thinking / Calling Bash / Done).

Out of scope: locking the composer, "session-done" signaling, or
trying to predict / annotate Claude's "I'll keep monitoring" phrases.

## Non-Goals

- **Session-idle / composer gating.** Forensics show alfred's
  existing result-driven unlock works correctly; there's no
  rejection storm to fix.
- **Subagent mini-chat rendering** (showing the subagent's own
  tool_use list inline). Defer to v0.5 — the lifecycle counter +
  description is enough for v0.4.
- **Hard wall-clock timeout on long prompts.** Users explicitly
  want multi-hour runs to be possible.

## Background: how Monitor and Agent actually behave

Confirmed by Claude Code hook docs and jsonl forensics on the
Oracle pod (`/home/alfred/.claude/projects/-home-alfred/b7bfc2fa-2ae2-4abc-b51c-c80cd851f6b2.jsonl`,
2026-06-17 session):

- **Monitor** is a CLI primitive: the bash command runs as a
  **detached background process**. The `tool_use_id` Monitor
  returned gets its `tool_result` immediately, and the result text
  always has the shape
  `Monitor started (task <task-id>, timeout <ms>ms). ...`. The
  parent claude-p process does not wait for the background process;
  the `result` event for the parent turn fires as soon as Claude's
  text finishes. Background output is reinjected into the session
  queue as `<task-notification>` user messages, drained at the next
  prompt.
- **Agent (subagent)** is dispatched via PreToolUse like any other
  tool. Claude Code emits dedicated lifecycle hooks
  `SubagentStart` and `SubagentStop` with `agent_id` and
  `agent_type` fields. These are the only reliable signal that a
  subagent started or finished — the parent turn's stream-json
  shows the Agent block "running" the whole time but with no
  intermediate progress.
- Claude Code's hook system supports `PostToolUse` (non-blocking,
  carries `tool_output`). Confirmed via docs at
  https://code.claude.com/docs/en/hooks.

## Architecture

Two data channels:

1. **Hook channel (extend existing Bridge):** PreToolUse stays as
   today; PostToolUse, SubagentStart, SubagentStop are added.
2. **Jsonl tailer (new):** watches the per-session jsonl for
   `queue-operation: enqueue` lines containing task-notification
   payloads. Extracts task-id, drives a per-task heartbeat. When a
   task-id stops getting enqueues for 90 s, it's declared ended.

```
┌────────────────────────────────────────────────────────────────┐
│  alfred-server                                                 │
│                                                                │
│  ┌─────────────────────┐    ┌──────────────────────────────┐   │
│  │ Bridge (existing)   │───▶│  ws.go asks handler          │   │
│  │  +PostToolUse       │    │  - PreToolUse  → tool_approval│  │
│  │  +SubagentStart     │    │  - PostToolUse → tool_done    │  │
│  │  +SubagentStop      │    │  - SubagentStart → subagent_started│
│  │  /tool-approval     │    │  - SubagentStop  → subagent_stopped│
│  │  endpoint           │    │                              │   │
│  └─────────────────────┘    └──────────────────────────────┘   │
│                                                                │
│  ┌──────────────────────┐   ┌──────────────────────────────┐   │
│  │ Jsonl tailer (new)   │──▶│  bg_task heartbeat tracker   │   │
│  │  per-session         │   │  task_id → lastEnqueueAt     │   │
│  │  fsnotify on .jsonl  │   │  90 s no-enqueue → ended     │   │
│  │  enqueue→parse XML   │   │  → bg_task_ended frame       │   │
│  └──────────────────────┘   └──────────────────────────────┘   │
└────────────────────────────────────────────────────────────────┘
```

The existing PreToolUse approval flow is unchanged. New hook
events flow through the same `Bridge.handleAsk` HTTP handler
(distinguished by `hook_event_name`) but respond immediately
(allow) instead of blocking on user decision.

The jsonl tailer is needed because the CLI's `queue-operation:
remove` events carry **no task_id** (verified by forensics:
11 task-ids in enqueues, 31 remove events with only timestamp and
sessionId). We therefore can't pair remove events with specific
Monitor tasks. The heartbeat approach is reliable instead:
forensics show every Monitor task in production emitted an
enqueue at least every 60 s during its active life, then went
silent on completion. 90 s is comfortable headroom.

## Components

### 1. Bridge hook registration (modify: `internal/claude/settings.go`,
`deploy/alfred-claude-bridge.sh`)

Today `EnsureSettingsHook` only registers `PreToolUse`. Extend to
register the same bridge script under three more event names:

```go
desiredEvents := []string{"PreToolUse", "PostToolUse", "SubagentStart", "SubagentStop"}
```

The script body is unchanged — same curl invocation, same endpoint.
The CLI passes `hook_event_name` in the stdin JSON, so the bridge
can switch on it. Idempotency check updated to verify all four
events point at our bridge.

### 2. Bridge handler dispatch (modify: `internal/claude/bridge.go`)

`PendingRequest` already includes `HookEventName`. Today
`handleAsk` always blocks waiting for a Resolve call. Update to:

- `PreToolUse` → existing blocking path (unchanged).
- `PostToolUse` → emit a separate callback (`onPostTool`), respond
  immediately with `{"hookSpecificOutput":{"hookEventName":"PostToolUse"}}`
  (empty allow).
- `SubagentStart` / `SubagentStop` → emit a separate callback
  (`onSubagent`), respond immediately.

The constructor signature gains two callbacks:

```go
func NewBridge(onAsk func(PendingRequest), onPostTool func(PostToolEvent), onSubagent func(SubagentEvent)) *Bridge
```

New payload structs (in `internal/claude/bridge.go`):

```go
type PostToolEvent struct {
    SessionID  string          // CLI's session UUID (caller maps to alfred sid)
    ToolUseID  string
    ToolName   string
    ToolInput  json.RawMessage
    ToolOutput json.RawMessage
}

type SubagentEvent struct {
    SessionID string
    HookEventName string  // SubagentStart | SubagentStop
    AgentID   string
    AgentType string
}
```

### 3. Dispatcher per-session subscription (modify:
`internal/claude/dispatcher.go`)

Today `dispatcher.SubscribeAsks(sid)` returns one channel of
PendingRequests. Add two parallel channels:

```go
func (d *Dispatcher) SubscribeAsks(sid string) (<-chan PendingRequest, func())
func (d *Dispatcher) SubscribePostTool(sid string) (<-chan PostToolEvent, func())
func (d *Dispatcher) SubscribeSubagent(sid string) (<-chan SubagentEvent, func())
```

Internal routing: dispatcher already maps CLI session UUID → alfred
sid. Apply the same lookup to PostTool / Subagent events.

### 4. WebSocket frames (modify: `internal/api/wsproto.go`,
`internal/api/ws.go`, `web/src/lib/ws.ts`)

Four new outbound message types:

```ts
type ServerMsg =
  // … existing …
  | { type: 'tool_done';        sessionID: string; toolUseId: string; toolName: string; output?: unknown; bgTaskId?: string; finishedAt: string }
  | { type: 'subagent_started'; sessionID: string; agentId: string; agentType: string; startedAt: string }
  | { type: 'subagent_stopped'; sessionID: string; agentId: string; finishedAt: string }
  | { type: 'bg_task_ended';    sessionID: string; bgTaskId: string; finishedAt: string }
```

Note `tool_done` carries an **optional** `bgTaskId` field. When
`toolName == "Monitor"`, the server regexes the output string —
`Monitor started \(task ([a-z0-9]+), timeout` — and sets
`bgTaskId` to the captured id. The frontend uses this to render
the Monitor's task id in the tool card as enrichment.

No new "intent" frame is added — the existing stream-json
`tool_use_start` already creates the tool block, and we found no
production case where the hook's earlier-by-~50ms timing would
have meaningfully helped the user.

### 5. Reducer changes (modify:
`web/src/features/sessions/claudeReducer.ts`,
`web/src/features/sessions/sessionsReducer.ts`,
`web/src/features/sessions/types.ts`)

`ClaudeToolCall` gains:

```ts
startedAt?: string   // set by tool_use_start reducer (Date.now() at create time)
finishedAt?: string  // set by tool_done reducer
bgTaskId?: string    // set by tool_done reducer for Monitor only
```

`ClaudeChatState` gains:

```ts
subagents: Map<string, { agentType: string; startedAt: string; finishedAt?: string }>
```

State transitions:

- `tool_use_start` (existing) — additionally records `startedAt =
  new Date().toISOString()` on the new block.
- `tool_done` (NEW) — patches the tool block by `toolUseId`: sets
  `finishedAt`, `bgTaskId`.
- `subagent_started` (NEW) — adds entry to `subagents` map.
- `subagent_stopped` (NEW) — patches `finishedAt` on the entry.

No state machine driving "session done" — `inFlight` continues
to mean exactly what it means today (parent `result` event seen).

### 6. UI changes (modify:
`web/src/features/sessions/ClaudeChatView.tsx`,
`web/src/features/sessions/WorkspacePage.tsx`,
`web/src/index.css`)

**(a) Per-tool elapsed in `ToolCallView`.** New `useElapsed(startedAt,
running)` hook: ticks every second; running flag = `!finishedAt`.
Display next to the status chip as `47s` / `2m14s` / `1h03m`. CSS
classes `is-slow` after 30 s (amber), `is-stuck` after 5 min (red).
Timer freezes on `finishedAt` and stays visible as historical
duration. When `tool.startedAt` is undefined (e.g. restored from
jsonl history without lifecycle frames), the elapsed display
hides itself.

**(b) Monitor enrichment.** When `tool.name === 'Monitor'` and
`tool.bgTaskId` is set, the collapsed row shows
`Monitor · task <id> · 12m` instead of the generic preview. The
expanded body shows the `description` field from input + the
`command` field collapsed under a "Show command" disclosure.

**(c) Subagent counter.** When `tool.name === 'Agent'`, the
collapsed row shows `Agent · <agentType> · running` while the
matching subagent entry has no `finishedAt`, and `Agent · done`
afterward. If multiple Agent tool calls are present in the same
turn, an aggregate chip in the turn header reads
`<runningCount>/<totalCount> subagents`.

**(d) Turn phase chip.** New chip in `ClaudeChatView` next to the
turn timestamp:

| Latest event observed                  | Chip text             |
| -------------------------------------- | --------------------- |
| `system`                               | Initializing          |
| `text_delta` (any)                     | Thinking              |
| `tool_use_start` (latest tool unfinished) | Calling `<toolName>`  |
| `result`                               | Done                  |

The chip reflects only the parent turn's phase. Background Monitor
tasks running after `result` are visible only as their own tool
cards (no special "still running" chip on the turn header).

### 7. Jsonl tailer (new file: `internal/claude/jsonl_tailer.go`)

Watches one jsonl per active Claude session via fsnotify, in the
same lifecycle pattern as `internal/summary/diskwatcher.go`
(close stop chan → wait done → close fsnotify). Spawned when a
session enters Claude UI mode; stopped on exit-Claude or session
delete.

Per-session state:

```go
type bgTaskTracker struct {
    mu        sync.Mutex
    lastSeen  map[string]time.Time  // task_id → last enqueue timestamp
    onEnded   func(taskID string)   // called when a task is declared ended
}
```

On each new jsonl line:

- Parse only entries with `"type": "queue-operation"` and
  `"operation": "enqueue"`. Everything else ignored.
- If `content` starts with `<task-notification>`, regex
  `<task-id>([a-z0-9]+)</task-id>` to extract the task id.
- Update `lastSeen[taskID] = ts`.

A separate goroutine wakes every 30 s and walks `lastSeen`. Any
task whose `lastSeen` is older than 90 s is declared ended:
`onEnded(taskID)` fires, `lastSeen` entry removed.

The `onEnded` callback emits a `bg_task_ended` WS frame:

```ts
| { type: 'bg_task_ended'; sessionID: string; bgTaskId: string; finishedAt: string }
```

Frontend reducer matches by `bgTaskId` to find the Monitor tool
block (set on `tool_done`) and patches its `finishedAt`. The
elapsed timer freezes; collapsed row changes from
`Monitor · task <id> · running 5m` to `Monitor · task <id> · done`.
Visual treatment: a small ✓ checkmark replaces the live-tick
indicator.

**Why 90 s threshold:** Production forensics show all 11 observed
Monitor tasks had an enqueue at least every 60 s during their
active phase (the polling loops emit a status line each iteration
even when state hasn't changed). 90 s = 1.5× headroom against a
slow loop iteration. False positives (declared done while still
running) would manifest as the card going ✓ and then bouncing
back to "running" when the next enqueue lands — handled by the
reducer clearing `finishedAt` if a fresh `bg_task_ended` doesn't
arrive but a tool-block update does.

### 8. Promise-mismatch banner (modify:
`web/src/features/sessions/claudeReducer.ts` and
`web/src/features/sessions/ClaudeChatView.tsx`)

Detects the "Claude said it would monitor / keep watching but
didn't actually dispatch a Monitor or Agent" case. Pure frontend
heuristic — no backend involvement, no new WS frame.

Trigger: in the `result` reducer case, after `last.done = true`,
inspect the turn:

```ts
const lastText = joinAssistantText(last.blocks).toLowerCase()
const promisedBackground = /\b(i'?ll|i will|let me)\s+(monitor|keep (watching|an eye)|track|let you know when|notify you when|report back|check back)\b/.test(lastText) ||
                           /\bin the background\b/.test(lastText)
const dispatchedBackground = last.blocks.some(b =>
  b.kind === 'tool' && (b.tool.name === 'Monitor' || b.tool.name === 'Agent')
)
if (promisedBackground && !dispatchedBackground) {
  last.promiseMismatch = true
}
```

`ClaudeTurn` gains optional `promiseMismatch?: boolean`.

`ClaudeChatView` renders a small banner below the assistant text
when `turn.promiseMismatch`:

```
ℹ Claude said it would monitor/check back, but no Monitor or
  Agent was dispatched — nothing is running in the background.
  Send a new prompt to check status.
```

Visual: amber/info color, dismissible (per-turn dismissal stored
in component state, not persisted — banner reappears on page
reload because the turn data is the truth source).

**False-positive containment.** The AND condition (`promised AND
not dispatched`) is strict: Claude can freely say "I'll keep
watching" as long as it actually dispatched Monitor — no banner.
Banner only appears when Claude's promise is genuinely empty.

## Data Flow Example

End-to-end for "push and monitor CI" scenario:

```
T0:    User sends prompt "push and monitor CI"
T0+0:  Backend: claude_handlers.go starts claude -p
T0+2:  PreToolUse hook fires for Bash(git push)
       → existing tool_approval_request frame (UNCHANGED)
       Frontend: claude-bypass-permissions auto-resolves, user sees nothing
T0+2:  stream-json tool_use_start arrives
       Frontend: creates Bash tool block with startedAt
T0+5:  PostToolUse hook for Bash
       → tool_done frame with finishedAt
       Frontend: freezes Bash elapsed at "3s"
T0+6:  PreToolUse for Monitor → existing flow
T0+7:  stream-json tool_use_start for Monitor → block created
T0+7:  PostToolUse for Monitor (immediate, the bash polling is detached)
       Output text is "Monitor started (task bbkgboee5, timeout 1800000ms)..."
       Bridge regexes "bbkgboee5" out → tool_done frame with bgTaskId
       Frontend: Monitor card shows "task bbkgboee5 · started 1s ago"
T0+7:  PreToolUse for Agent(task=research X) → existing flow
T0+7:  stream-json tool_use_start for Agent
T0+8:  SubagentStart hook fires
       → subagent_started frame
       Frontend: Agent card shows "agentType · running" + elapsed ticker
T2m:   SubagentStop hook
       → subagent_stopped frame
       Frontend: Agent elapsed freezes
T2m+1: stream-json tool_result for Agent → existing flow, fills result text
T2m+5: stream-json result for parent turn → inFlight = false
       Frontend: turn phase chip = "Done"; Monitor card still
       shows live elapsed; promise-mismatch banner NOT triggered
       (Monitor block exists in turn.blocks)
T2m+8 → T7m: Jsonl tailer parses task-notification enqueues for
       task bbkgboee5 every 30s (the polling script's heartbeat)
       lastSeen[bbkgboee5] keeps updating
T7m+5: CI completes, polling script exits → no more enqueues
T7m+95: Heartbeat sweep finds bbkgboee5 silent > 90s
       → bg_task_ended frame with bgTaskId=bbkgboee5
       Frontend: Monitor card freezes "5m02s · ✓ done"
```

## Error Handling

| Failure                                       | Behavior                                                                                                  |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| PostToolUse hook never fires                  | Tool block keeps its startedAt forever (elapsed keeps ticking). Existing `tool_result` stream event still patches the result text. Worst case: a visual "running forever" until the next result. |
| SubagentStop hook never fires                 | Subagents map entry stays without finishedAt. UI shows "running" until next session reset. Acceptable degradation. |
| Hook fires for a session UUID we don't recognize | Dispatcher already drops these (existing FindByClaudeConvoID logic).                                     |
| Bridge HTTP unreachable                       | Existing behavior — CLI denies the tool. No new failure modes.                                            |
| Monitor output text doesn't match the task-id regex | bgTaskId left unset. Tool card still renders, just without the task id enrichment.                  |
| History restore creates blocks without startedAt | `useElapsed` short-circuits on undefined startedAt; chip hides. No crash.                            |
| Jsonl tailer can't open the jsonl file        | Log + skip — Monitor cards will keep ticking elapsed forever for that session, but no crash. Heartbeat tracker is best-effort. |
| Bg task declared ended (90s silence) but then enqueue resumes | Reducer un-sets `finishedAt` on next tool block update for that bgTaskId. Card returns to running state. User sees brief ✓ then back to live ticker. |
| Promise-mismatch false positive (Claude actually did dispatch via a tool we don't detect) | Banner shown unnecessarily. Mitigation: banner is dismissible. Detection list (Monitor, Agent) is the full set of CLI background-capable tools per docs. |

## Migration / Backwards Compatibility

- No existing WS frame's shape changes. Old clients ignore the
  four new frame types and degrade gracefully (no per-tool
  elapsed, no subagent counter, no Monitor enrichment, no Monitor
  done state, no promise-mismatch banner — only client-side).
- Settings.json patch is additive — hooks already present for
  PreToolUse stay, new entries added for the other three.
- History-restore tool blocks have no startedAt / finishedAt;
  reducer-level fallback already covered (`useElapsed` hides
  when undefined).

## Rollout

Single PR. Merge to `next`, tag `v0.4`, deploy as usual. No flag —
strictly additive UX improvements.
