# v0.4 Tool-Lifecycle Transparency Design

**Date:** 2026-06-17
**Status:** Pending review (v3 — pure stream-json approach)
**Predecessors:** [`2026-06-13-claude-ui-mode-design.md`](2026-06-13-claude-ui-mode-design.md), [`2026-06-15-summary-template-design.md`](2026-06-15-summary-template-design.md)

## Problem

When a Claude turn dispatches a `Monitor` tool (long-running
background polling) or an `Agent` subagent (synchronous tool with no
intermediate progress visible to the parent), the user cannot see:

- Which subagents are currently running.
- Which Monitor tasks were dispatched, by which `task_id`, with
  what description.
- Whether a long-running task is still alive or has completed.
- How long each tool has been running.
- Whether Claude's "I'll monitor CI and report back" statement
  corresponds to anything actually dispatched.

Concrete pain (oracle pod, jsonl forensics 2026-06-17): during one
session the user sent "检查的如何 / 咋样了? / 你一直运行一直检查" every
5–15 minutes because the UI showed nothing about 11 dispatched
Monitors and 11 dispatched Agents.

A separate confusion was suspected — that the "another prompt is
still in flight" rejection fires because the CLI is still draining
background notifications. **Forensics ruled this out**: alfred
releases its `runStates` slot the moment the `result` event arrives
([`claude_handlers.go:524`](../../../internal/api/claude_handlers.go)),
and the jsonl shows zero cases where the user's next prompt fired
faster than that release.

## Goal

Use the Claude CLI's own task / hook lifecycle events — already
present in the stream-json output when `--include-hook-events` is
passed — as the **single, authoritative ground truth** for every
piece of UI we add. No heuristics, no timeouts, no regex on
Claude's prose.

The user gets:

- A live count and list of active background Monitor tasks per
  session, with task description and elapsed time.
- A live count and list of active subagents per session, with
  agent type and elapsed time.
- Per-tool elapsed display for every tool call.
- A turn-level phase chip (Initializing / Thinking / Calling Bash /
  Done) driven by the existing stream.
- A factual per-turn stats line at the end of each turn:
  "This turn dispatched: N tool calls, M Monitor tasks, K
  subagents." Lets the user see at a glance whether Claude's
  promise to "monitor" or "check back" was backed by an actual
  dispatch — without us writing a banner that judges Claude's
  prose.

## Non-Goals

- **Session-idle / composer gating.** Forensics show alfred's
  existing result-driven unlock works correctly.
- **Wall-clock timeout on long prompts.** Users want multi-hour
  runs.
- **Banner that scans Claude's text for "I'll monitor".** Replaced
  by the factual stats line — the user sees what was dispatched
  and judges for themselves.
- **Heuristic Monitor completion detection.** The CLI emits
  `task_updated.status=completed` directly; we use that, full stop.
- **Subagent mini-chat rendering** (showing the subagent's own
  tool_use list inline). Defer to v0.5.
- **Extending the existing PreToolUse Bridge for new hook
  routing.** The bridge stays as it is for approval; everything
  else flows through stream-json.

## Background: ground-truth events from `--include-hook-events`

Verified by running `claude -p --output-format=stream-json
--include-hook-events --verbose --dangerously-skip-permissions
"..."` on the oracle pod (2026-06-17). The CLI emits these
event shapes via stdout, interleaved with the existing assistant /
user / result events:

```jsonc
// Monitor dispatched
{"type":"system","subtype":"task_started",
 "task_id":"barwhkp36",
 "tool_use_id":"toolu_01ARh68iaWfJABW3Fg4j5ZBF",
 "description":"echo line1-3 with 5s sleeps",
 "task_type":"local_bash",
 "session_id":"<uuid>"}

// Monitor emits a notification (each stdout line during run)
{"type":"system","subtype":"task_notification",
 "task_id":"barwhkp36",
 "tool_use_id":"toolu_01ARh68iaWfJABW3Fg4j5ZBF",
 "status":"in_progress",  // or "completed" on final
 "summary":"Monitor \"echo line1-3 with 5s sleeps\" event",
 "session_id":"<uuid>"}

// Monitor finished (the GROUND TRUTH end signal)
{"type":"system","subtype":"task_updated",
 "task_id":"barwhkp36",
 "patch":{"status":"completed","end_time":1781706396034},
 "session_id":"<uuid>"}

// Every hook the CLI invokes (PreToolUse, PostToolUse,
// SubagentStart, SubagentStop, Notification, etc.) appears as:
{"type":"system","subtype":"hook_started",
 "hook_id":"<uuid>",
 "hook_name":"PreToolUse:Bash",
 "hook_event":"PreToolUse",
 "session_id":"<uuid>"}
{"type":"system","subtype":"hook_response",
 "hook_id":"<uuid>",
 "hook_event":"PreToolUse",
 "output":"...",  // raw hook stdout
 "exit_code":0,
 "outcome":"success",
 "session_id":"<uuid>"}

// CLI re-invokes itself to drain task notifications.
// Distinguishable by origin.kind on the result.
{"type":"result","subtype":"success",..., "origin":{"kind":"task-notification"}}
```

Crucial properties:

- **`task_started` carries both `task_id` AND `tool_use_id`.** We
  can match the Monitor's UI tool block (keyed by tool_use_id) to
  the long-running task (keyed by task_id) without any regex.
- **`task_updated` with `status=completed`** is the canonical
  Monitor-done signal. No 90 s heartbeat needed.
- **Subagent lifecycle** also surfaces through `hook_started` /
  `hook_response` for `hook_event in {SubagentStart, SubagentStop}`.
  Same channel, same parser entry point.
- **No new infrastructure required.** Alfred's existing
  `internal/claude/parser.go` is already parsing stream-json from
  the spawned `claude -p` process. We just need to recognize the
  new `system.subtype` values.

## Architecture

One change: pass `--include-hook-events` to the `claude -p`
invocation, and extend the stream-json parser to recognize the
new `system.subtype` events. Everything else (Bridge, dispatcher,
WS protocol envelope) stays the same.

```
┌─────────────────────────────────────────────────────────────┐
│  claude -p --output-format=stream-json                      │
│         --include-hook-events  ← NEW FLAG                   │
│                                                             │
│  stdout → existing parser → new event variants:             │
│     task_started, task_notification, task_updated           │
│     hook_started, hook_response                             │
│                                                             │
│  → existing claude_event WS frame → reducer → UI            │
└─────────────────────────────────────────────────────────────┘
```

No new WS frame types are needed at the protocol level — we extend
the existing `claude_event` envelope's `eventKind` enum. No new
hook scripts. No `~/.claude/settings.json` patch beyond what's
already there for PreToolUse approval. No jsonl tailer.

## Components

### 1. CLI invocation flag (modify: `internal/claude/runner.go`)

Add `--include-hook-events` to the `exec.Cmd` args list built in
`Runner.Prompt`. This is the single backend wiring change.

### 2. Parser additions (modify: `internal/claude/parser.go`,
`internal/claude/event.go`)

The existing parser handles `type=system` lines by dispatching on
`subtype`. Add cases for:

- `task_started` → emit `Event{Kind: KindTaskStarted, TaskStarted: &TaskStartedEvent{TaskID, ToolUseID, Description, TaskType}}`
- `task_notification` → emit `Event{Kind: KindTaskNotification, TaskNotification: &TaskNotificationEvent{TaskID, ToolUseID, Status, Summary}}`
- `task_updated` → emit `Event{Kind: KindTaskUpdated, TaskUpdated: &TaskUpdatedEvent{TaskID, Status, EndTime}}`
- `hook_started` → emit `Event{Kind: KindHookStarted, HookStarted: &HookStartedEvent{HookID, HookEvent, HookName}}`
- `hook_response` → emit `Event{Kind: KindHookResponse, HookResponse: &HookResponseEvent{HookID, HookEvent, ExitCode, Outcome}}`

Add the corresponding payload structs and `EventKind` constants in
`event.go`. Existing parser tests are extended with one new
fixture per event type (captured from real pod output).

### 3. WS protocol — extend existing `claude_event` (modify:
`internal/api/claude_handlers.go`, `web/src/lib/ws.ts`)

`claude_event` envelope already carries `eventKind: string` and
`payload: unknown`. The new event kinds become valid values:

```ts
export type ClaudeEventKind =
  | 'system'
  | 'rate_limit'
  | 'text_delta'
  | 'text_block_end'
  | 'thinking_delta'
  | 'tool_use_start'
  | 'tool_use_end'
  | 'tool_result'
  | 'message_start'
  | 'message_delta'
  | 'message_stop'
  | 'result'
  | 'task_started'        // NEW
  | 'task_notification'   // NEW
  | 'task_updated'        // NEW
  | 'hook_started'        // NEW
  | 'hook_response'       // NEW
  | 'unknown'
```

`claudeEventPayload` in `claude_handlers.go` gains five `case`
branches forwarding the new payloads. No new top-level WS message
type — backwards-compatible because old clients see unknown
`eventKind` and fall through (`unknown`).

### 4. Reducer changes (modify:
`web/src/features/sessions/claudeReducer.ts`,
`web/src/features/sessions/types.ts`)

New shapes:

```ts
export interface BgTask {
  taskId: string
  toolUseId: string  // links to ClaudeToolCall.toolUseId for Monitor
  description: string
  taskType: string   // 'local_bash' | future variants
  startedAt: string
  finishedAt?: string  // set when task_updated.status='completed'
  status: 'in_progress' | 'completed' | 'failed'
  lastEventSummary?: string  // from latest task_notification
  notificationCount: number
}

export interface SubagentEntry {
  hookId: string     // pairs hook_started with hook_response
  agentType?: string
  startedAt: string
  finishedAt?: string
}
```

`ClaudeChatState` gains:

```ts
bgTasks: Map<string, BgTask>           // keyed by taskId
subagents: Map<string, SubagentEntry>  // keyed by hookId
```

`ClaudeToolCall` gains:

```ts
startedAt?: string   // set by tool_use_start reducer (Date.now())
finishedAt?: string  // set by tool_result reducer
bgTaskId?: string    // set when a matching task_started arrives
```

Reducer transitions:

- `tool_use_start` (existing) — additionally record `startedAt`.
- `tool_result` (existing) — additionally record `finishedAt`.
- `task_started` (NEW) — insert into `bgTasks`; if its
  `toolUseId` matches a tool block, set that block's `bgTaskId`.
- `task_notification` (NEW) — bump `notificationCount`, update
  `lastEventSummary`. If `status === 'completed'`, treat the same
  as `task_updated.status=completed`.
- `task_updated` (NEW) — if `patch.status === 'completed'`, set
  `bgTasks[taskId].finishedAt = patch.end_time`, status='completed'.
- `hook_started` with `hook_event === 'SubagentStart'` (NEW) —
  insert into `subagents` keyed by `hookId`.
- `hook_response` with `hook_event === 'SubagentStop'` (NEW) —
  patch `finishedAt`. (SubagentStart's hook_response is fired
  immediately; the matching SubagentStop hook is what we wait for.)
- Other `hook_started` / `hook_response` — ignored for now (could
  power debug overlay later).

### 5. UI changes (modify:
`web/src/features/sessions/ClaudeChatView.tsx`,
`web/src/features/sessions/WorkspacePage.tsx`,
`web/src/index.css`)

**(a) Per-tool elapsed in `ToolCallView`.** `useElapsed(startedAt,
finishedAt)` hook ticks every second when `!finishedAt`. Display
`47s` / `2m14s` / `1h03m` next to status chip. `is-slow` after
30 s (amber), `is-stuck` after 5 min (red). Timer freezes on
`finishedAt`. When `startedAt` is undefined (history restore from
old jsonl without `--include-hook-events`), the display hides.

**(b) Monitor enrichment.** When `tool.name === 'Monitor'` and
`tool.bgTaskId` is set, the collapsed row shows
`Monitor · task <id> · 12m · 47 events` (the count from
`bgTasks[bgTaskId].notificationCount`). When the bg task is
`completed`, a ✓ replaces the ticker and elapsed freezes at the
final value. Expanded body shows description + last event summary.

**(c) Subagent indicator.** When `tool.name === 'Agent'`, the
collapsed row shows `Agent · running 2m14s` while at least one
matching subagent entry has no `finishedAt`, otherwise
`Agent · done 3m02s`. (The matching is by enclosing turn — every
subagent dispatched during the turn becomes the Agent's
representative.)

**(d) Turn phase chip.** Next to turn timestamp:

| Latest event observed                            | Chip text             |
| ------------------------------------------------ | --------------------- |
| `system.init`                                    | Initializing          |
| `text_delta` (any)                               | Thinking              |
| `tool_use_start` (latest tool unfinished)        | Calling `<toolName>`  |
| `result`                                         | Done                  |

**(e) Turn factual stats.** Below the assistant text, when the
turn is `done`, a one-line muted stats label:

```
3 tool calls · 1 Monitor task (running) · 2 subagents (done)
```

Counts derived from the turn's `blocks` + matching `bgTasks` +
`subagents`. **This replaces the planned "promise mismatch
banner"**: the user sees the actual dispatch counts and can judge
whether Claude's words match — no inference by us. If Claude said
"I'll monitor CI" but the stats line shows "0 Monitor tasks", the
truth is in front of them without us telling them so.

**(f) Per-session active-task pill.** In the session list (left
sidebar): when `bgTasks.size > 0 || subagents.size > 0` for a
session, show a small badge next to the session name: `⏳ 2`.
Tooltip enumerates task descriptions.

## Data Flow Example

```
T0:    User: "push and monitor CI"
T0+0:  Backend: claude_handlers.go starts claude -p WITH
       --include-hook-events
T0+2:  stream-json: tool_use_start (Bash)
       → tool block created, startedAt = now
T0+2:  stream-json: hook_started (PreToolUse:Bash)
       Reducer: ignored (not subagent)
T0+2:  stream-json: hook_response (PreToolUse:Bash)
T0+5:  stream-json: tool_result (Bash) → block.finishedAt
T0+6:  stream-json: tool_use_start (Monitor)
T0+7:  stream-json: hook_started/response (PreToolUse:Monitor)
T0+7:  stream-json: task_started
         task_id=barwhkp36, tool_use_id=toolu_01ARh...
       → bgTasks['barwhkp36'] inserted, status=in_progress
       → ClaudeToolCall.bgTaskId set on the Monitor block
T0+7:  stream-json: tool_result (Monitor — short "started" string)
       → block.finishedAt set, but bgTaskId means the UI keeps
         showing the background task tracker
T0+8:  stream-json: tool_use_start (Agent)
T0+8:  stream-json: hook_started (SubagentStart) → subagents map +
T2m:   stream-json: hook_response (SubagentStop) → subagents patched
T2m+1: stream-json: tool_result (Agent)
T2m+5: stream-json: result (parent turn) → turn.done=true
       UI: phase chip "Done", stats line renders:
         "5 tool calls · 1 Monitor task (running) · 1 subagent (done)"
T3m:   stream-json: task_notification (barwhkp36, in_progress)
       → bgTasks count++, lastEventSummary updated
       (this arrives via the CLI's auto-re-invocation; alfred's
       parser doesn't care, it just forwards the event)
T7m:   stream-json: task_updated (barwhkp36, status=completed)
       → bgTasks['barwhkp36'].finishedAt set
       UI: Monitor card freezes "5m02s · ✓ completed", stats line
       updates to "5 tool calls · 1 Monitor task (done) · 1 subagent (done)"
       Sidebar pill: badge disappears
```

## Error Handling

| Failure                                       | Behavior                                                                                                              |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `task_updated` never arrives (CLI bug)        | bg task stays in_progress forever in UI. User sees it ticking, but no other broken state. Reload clears it from history (next session start). |
| `--include-hook-events` flag not supported by the running CLI version | The parser sees no `task_*` events; the UI degrades silently (no bg task tracker, no subagent counter). All other features still work. The CLI version that ships with alfred (Dockerfile-pinned) is verified to support it. |
| Two `task_started` with same task_id          | Reducer overwrites; only later one tracked. Logged but not surfaced.                                                  |
| `task_started.tool_use_id` doesn't match any tool block | bgTask still tracked under bgTasks map; just isn't linked to a Monitor card. Tooltip in the sidebar pill remains usable. |
| Hook event for unknown session UUID           | Dispatcher already drops these (existing FindByClaudeConvoID logic).                                                  |
| History restore creates blocks without startedAt | `useElapsed` short-circuits on undefined; chip + bg-task tracker hide cleanly. No crash.                          |
| Subagent's StopHook never fires               | Subagent entry stays in `subagents` map. UI shows "running" forever for that turn. Acceptable degradation.            |

### E2E (long, realistic task scenarios)

The E2E suite specifically exercises long-running and complex
flows — short happy-path tests would not catch the lifecycle
edge cases this feature targets.

Add `web/e2e/long-running-tools.spec.ts` with these cases:

- **`bg_task_lifecycle_completes`**: drive a session that
  dispatches `Monitor` with a 30-second polling bash command.
  Assert the Monitor card appears with bgTaskId, shows live
  notification count climbing for ≥3 events, then freezes with ✓
  when `task_updated.status=completed` arrives.

- **`subagent_long_running_5min`**: dispatch an Agent that
  invokes general-purpose subagent with a multi-step task
  (e.g., "list the 20 largest files under /tmp"). Assert:
  - Agent tool block appears with startedAt
  - SubagentStart hook event lands → subagents map entry
  - Parent turn's phase chip shows "Calling Agent" the whole time
  - On SubagentStop hook → subagents entry patched, Agent card
    freezes elapsed
  - tool_result then fills the result text
  Verify elapsed timer never glitches (no zero, no negative,
  monotonic).

- **`multiple_concurrent_monitors`**: prompt that dispatches 3
  Monitor tasks in one turn (e.g., "monitor these three log
  files in parallel for 30s each"). Assert all 3 appear in the
  sidebar pill (`⏳ 3`), 3 separate bgTask entries, completion
  order is correctly tracked (one finishing doesn't affect the
  others).

- **`stats_line_truth_test`**: prompt that says "I'll monitor
  CI for you" but explicitly does NOT dispatch Monitor (use a
  prompt like "Just say you'll monitor, don't actually use any
  tools"). Assert the turn stats line says `0 tool calls · 0
  Monitor tasks · 0 subagents`. Then prompt one that DOES
  dispatch Monitor. Assert stats correctly shows `1 Monitor
  task`. This is the "promise mismatch" coverage — fact-based,
  no banner.

- **`monitor_completes_after_parent_result`**: dispatch a
  60-second Monitor, watch the parent turn's `result` fire
  before the Monitor completes. Assert: Monitor card keeps
  ticking after `Done` chip on turn header. When
  `task_updated.completed` eventually arrives (via the CLI's
  re-invocation), Monitor card freezes ✓. **This is the v0.4
  core success criterion.**

- **`subagent_failure_path`**: dispatch a subagent that the user
  cancels (via Stop button — already exists). Assert SubagentStop
  hook fires with a non-success outcome, subagents entry patched
  with finishedAt, no spinner stuck.

## Migration / Backwards Compatibility

- New WS protocol values are additive (`eventKind` enum extension).
  Old clients see unknown values and fall through.
- The Dockerfile-pinned claude CLI version (currently
  2.1.142, verified) supports `--include-hook-events`. Upgrade
  policy: if a future CLI version regresses on this flag, the UI
  loses the new lifecycle features but everything else keeps
  working — no hard dependency.
- History restore creates tool blocks without startedAt /
  finishedAt / bgTaskId; UI degrades cleanly (`useElapsed` and
  the bg-task tracker hide).
- `~/.claude/settings.json` unchanged. No new hook scripts.

## Rollout

Single PR. Merge to `next`, tag `v0.4`, deploy as usual. No flag —
strictly additive UX improvements. The CLI version pin in the
Dockerfile is the only deploy-side change beyond code.

## Out of Scope (Future Work)

- **Subagent mini-chat** (v0.5): expose the subagent's own
  tool_use list inline via parent_tool_use_id correlation.
- **Per-tool stdout streaming** for Bash in real time (would
  need different mechanism — Bash isn't a task).
- **Browser notification** when a long task completes while
  the tab is backgrounded.
- **Cancel a running Monitor task from the UI**: the CLI has a
  `TaskStop` tool but exposing it requires a new WS verb. Defer.
