# v0.4 Tool-Lifecycle Transparency Design

**Date:** 2026-06-17
**Status:** Approved (pending final review)
**Predecessors:** [`2026-06-13-claude-ui-mode-design.md`](2026-06-13-claude-ui-mode-design.md), [`2026-06-15-summary-template-design.md`](2026-06-15-summary-template-design.md)

## Problem

The frontend cannot tell when a Claude turn is **actually** done. Today
the `result` stream-json event is the only "this turn finished"
signal — but Claude's CLI runs `Monitor` tools and `Agent` subagents
as background tasks that **outlive** the `result` event. Concretely,
in production we observed all of these:

1. `result` event arrives at T0. UI clears the spinner. User assumes
   the turn is done and types a new prompt. Backend rejects with
   `another prompt is still in flight` because Monitor pollers are
   still enqueueing `task-notification` messages and the CLI is
   still draining them on the same `claude -p` invocation.
2. Claude's final assistant text says "I'll monitor CI and report
   back." The UI shows this message right when the spinner clears.
   The user has no way to tell whether something actually IS
   monitoring (sometimes Monitor was dispatched, sometimes Claude
   just said it would).
3. A subagent (`Agent` tool) is dispatched. The parent turn looks
   inert for 2 minutes while the subagent runs 11 of its own
   tool_use calls. Frontend shows one spinner with no progress.

The shared root cause: **the truth source for "turn complete" lives
in two places that the frontend has never seen** — the CLI's
internal task queue (`queue-operation` events in the jsonl) and
the PreToolUse / PostToolUse hook stream.

## Goal

Give the frontend a single, authoritative `session_idle` signal that
fires only when:

- The main `result` event arrived, AND
- Every background task (Monitor pollers, Agent subagents) that this
  turn dispatched has completed.

Until that signal arrives, the composer is **disabled** and the
session card shows what's still running (`2 background tasks · Agent,
Monitor`). When it arrives, the composer unlocks.

As secondary wins, the same plumbing enables per-tool elapsed-time
display ("Bash · 47s") and a turn-level phase chip
("Thinking" / "Calling Bash" / "Done").

## Non-Goals

- Subagent mini-chat rendering (showing the subagent's own tool_use
  list inline). Defer to v0.5 — the subagent's lifecycle counter is
  enough for v0.4.
- Hard wall-clock timeout on long prompts. Users explicitly want
  multi-hour runs to be possible.
- Server-side anti-pattern footer in templates (rejected: Monitor is
  a legitimate tool, we shouldn't tell Claude not to use it).
- Hallucination-detection banner that scans Claude's text for "I'll
  monitor…" phrases. Made obsolete by `session_idle` — if the
  composer stays locked, the user can see Claude really is monitoring.

## Background: how Monitor and Agent actually behave

Confirmed by jsonl forensics on Oracle pod
(`/home/alfred/.claude/projects/-home-alfred/b7bfc2fa-2ae2-4abc-b51c-c80cd851f6b2.jsonl`,
2026-06-17 session):

- The CLI runs the `Monitor` tool's bash command as a **detached
  background process**. Each line of stdout it emits becomes a
  synthesized user message of the form:
  ```xml
  <task-notification>
    <task-id>bbkgboee5</task-id>
    <summary>Monitor event: "CI workflow status on ci/github-actions"</summary>
    <event>[07:02:50] polling https://api.github.com/…</event>
  </task-notification>
  ```
  These messages land in the CLI's input queue and surface in the
  jsonl as `queue-operation: enqueue` entries.
- When the Monitor process exits, the CLI emits a
  `queue-operation: remove` with the same `task-id`.
- The `tool_use_id` Monitor returned (which the parent assistant
  message references) is **not** the same as the `task-id`. The
  `tool_use_id` gets its `tool_result` immediately (with the message
  "Started monitor task <task-id>"); the real long-running work is
  tracked by the `task-id`.
- 11 of 11 observed Monitor dispatches in that transcript had
  near-instant `tool_result` (<100 ms); 4 of them subsequently had
  zero `task-notification` enqueues (script exited immediately due
  to GitHub auth failure); 7 ran for minutes and the CLI re-invoked
  itself to drain the task-notifications.

`Agent` (the subagent tool) behaves differently — it blocks the
parent's stream-json output until the subagent finishes, and its
`tool_use_id` only gets a `tool_result` at the end. So Agent shows
up to the parent process as one long-running synchronous tool call.

This means the truth source for "background task still running"
is **`queue-operation: enqueue` minus matching `queue-operation:
remove`**, observed by tailing the per-session jsonl.

## Architecture

Two new data channels feed a single per-session **lifecycle tracker**
that lives in alfred-server. The tracker produces one new outbound
WebSocket frame: `session_idle`. Existing frames are unchanged.

```
┌──────────────────────────────────────────────────────────────────┐
│  alfred-server                                                   │
│                                                                  │
│  ┌────────────────┐    ┌───────────────────────┐                 │
│  │ jsonl tailer   │───▶│  Lifecycle Tracker    │───▶ session_idle│
│  │ (queue-ops)    │    │  per-session state    │     WS frame    │
│  └────────────────┘    │  ─────────────────    │                 │
│                        │  inFlightToolUseIds   │                 │
│  ┌────────────────┐    │  pendingBgTaskIds     │                 │
│  │ PreToolUse hook│───▶│  resultSeen bool      │───▶ tool_intent │
│  │ PostToolUse    │    │                       │     tool_done   │
│  │ (Bridge)       │    │                       │     WS frames   │
│  └────────────────┘    └───────────────────────┘                 │
└──────────────────────────────────────────────────────────────────┘
```

Both channels are needed:

- **jsonl tailer (A)** is the only source of `queue-operation`
  events. `task-id` is invisible to the hook channel because it's
  generated internally by the CLI after the tool returns.
- **Hook channel (B)** is the only source of pre-flight tool intent
  (the input JSON) before the stream-json `tool_use_start` event
  arrives. Also the only place to get exact stdout/exit-code on
  PostToolUse for tools that aren't `Monitor`.

## Components

### 1. Jsonl tailer (new file: `internal/claude/jsonl_tailer.go`)

Watches one jsonl per active Claude session via fsnotify. Parses
each newly appended line. Surfaces only the events the lifecycle
tracker cares about:

```go
type JSONLEvent struct {
    Kind      JSONLEventKind  // QueueEnqueue, QueueRemove
    SessionID string          // alfred session id (the convo uuid → alfred sid lookup happens in caller)
    TaskID    string          // for queue ops only
    Content   string          // for QueueEnqueue: the inline content (lets us classify Monitor vs user prompt)
    Timestamp time.Time
}
```

The tailer follows the same "open + seek + fsnotify on append"
pattern as `internal/summary/diskwatcher.go` to keep the lifecycle
similar (close stop chan → wait done → close fsnotify). One tailer
per session; spawned when a session enters Claude mode, stopped
when it exits.

Lines that aren't `queue-operation` are ignored. Tool_use and
tool_result entries also already arrive through stream-json on
the existing path; we don't double-emit.

### 2. Hook channel extension (modify: `internal/claude/bridge.go`,
`deploy/alfred-claude-bridge.sh`, `internal/claude/settings.go`)

Today only `PreToolUse` is registered, and it's used only for
permission approval (POST → block → response). Two changes:

- Register `PostToolUse` too. Same script, same endpoint — body
  shape differs by `hook_event_name`.
- Bridge handler **always** emits a `tool_intent` (PreToolUse) or
  `tool_done` (PostToolUse) callback to the lifecycle tracker
  before blocking on approval. The approval blocking semantics
  for PreToolUse are unchanged. PostToolUse responds immediately
  (CLI doesn't gate on its decision; we just allow).

The intent fires for **every** tool, not just Monitor/Agent. This
makes the same plumbing power per-tool elapsed and the phase chip.

### 3. Lifecycle tracker (new file: `internal/api/lifecycle.go`)

Per-session state, lives in the WS handler scope (one map keyed
by alfred sid, parallel to `claudeRunStateMap`).

```go
type lifecycleState struct {
    inFlightToolUseIDs map[string]toolMeta  // PreToolUse seen, PostToolUse not yet
    pendingBgTaskIDs   map[string]struct{}  // QueueEnqueue seen, QueueRemove not yet
    resultSeen         bool                 // main turn `result` event arrived
    startedAt          time.Time
}

type toolMeta struct {
    name      string
    input     json.RawMessage
    startedAt time.Time
}
```

State transitions:

| Event              | Mutation                                    | Emit?        |
| ------------------ | ------------------------------------------- | ------------ |
| tool_intent (Pre)  | inFlightToolUseIDs[id] = meta               | tool_intent  |
| tool_done (Post)   | delete(inFlightToolUseIDs, id)              | tool_done    |
| QueueEnqueue       | pendingBgTaskIDs[task-id] = {}              | bg_task_start (only if content matches task-notification shape — user prompts also enqueue) |
| QueueRemove        | delete(pendingBgTaskIDs, task-id)           | bg_task_end  |
| stream `result`    | resultSeen = true                           | (unchanged)  |
| **(any of above)** | if resultSeen && len(both maps) == 0 → idle | session_idle |

The `session_idle` frame is emitted **at most once** per turn.
When the next prompt fires, state resets.

Why classify QueueEnqueue content: ordinary user prompts also
appear as `queue-operation: enqueue` (you can see this in the
forensics — every prompt the user sent shows up). We only treat
entries whose `content` begins with `<task-notification>` as
background tasks. User-prompt enqueues are ignored.

### 4. New WebSocket frames (modify: `internal/api/wsproto.go`,
`web/src/lib/ws.ts`)

Four new outbound message types. All carry `sessionID` so the
frontend dispatches to the right per-session reducer.

```ts
type ServerMsg =
  // … existing variants …
  | { type: 'tool_intent'; sessionID: string; toolUseId: string; name: string; input: unknown; startedAt: string }
  | { type: 'tool_done';   sessionID: string; toolUseId: string; output?: string; isError?: boolean; finishedAt: string }
  | { type: 'bg_task_start'; sessionID: string; taskId: string; summary: string; startedAt: string }
  | { type: 'bg_task_end';   sessionID: string; taskId: string; finishedAt: string }
  | { type: 'session_idle';  sessionID: string }
```

The stream-json-derived `claude_event` frames keep flowing
unchanged. `tool_use_start` becomes a frontend no-op (see Reducer
Changes); `tool_use_end` and `tool_result` still patch the
existing tool block (carry the actual input JSON / result string
that hooks may not capture verbatim).

### 5. Reducer changes (modify:
`web/src/features/sessions/claudeReducer.ts`,
`web/src/features/sessions/sessionsReducer.ts`,
`web/src/features/sessions/types.ts`)

`ClaudeToolCall` gains:

```ts
startedAt?: string   // populated from tool_intent
finishedAt?: string  // populated from tool_done
```

`ClaudeChatState` gains:

```ts
bgTasks: Map<string, { summary: string; startedAt: string }>
sessionIdle: boolean   // mirrors backend session_idle; replaces "inFlight === false" for composer-gating
```

State transitions:

- `tool_intent` → create the tool block (today this happens in
  `tool_use_start`). If a `tool_use_start` arrives for the same
  `toolUseId` afterward, it's a no-op (idempotent block creation).
- `tool_done` → set `finishedAt`; leave `result` patching to the
  existing `tool_result` event (hook output may be incomplete or
  differently formatted vs stream-json's `tool_result`).
- `bg_task_start` / `bg_task_end` → update `bgTasks` map.
- `session_idle` → set `sessionIdle = true`.

Composer `disabled` prop now reads `!sessionIdle && hasActiveTurn`
instead of `inFlight`, where `hasActiveTurn` is true iff the last
turn in `turns[]` exists and isn't `done`. This means the composer
unlocks on `session_idle` (post-prompt with no bg tasks left) AND
on the natural empty-state (no prompt sent yet — sessionIdle
starts as `true`).

### 6. UI changes (modify:
`web/src/features/sessions/ClaudeChatView.tsx`,
`web/src/features/sessions/WorkspacePage.tsx`,
`web/src/index.css`)

Three visible pieces:

**(a) Per-tool elapsed in `ToolCallView`.** Use `tool.startedAt` →
client-side `useElapsed(startedAt, running)` hook ticks every
second. Display next to the status chip. Class `is-slow` after
30 s (amber), `is-stuck` after 5 min (red + warning icon). The
timer freezes on `finishedAt` and stays visible as historical
duration.

**(b) Turn phase chip** in `ClaudeChatView` next to the turn timestamp.
Driven by existing event sequence:

| Latest event observed       | Chip text                |
| --------------------------- | ------------------------ |
| `system`                    | Initializing             |
| `text_delta`                | Thinking                 |
| `tool_intent` (latest tool) | Calling `<toolName>`     |
| `bg_task_start` (≥1)        | Background: `<count>`    |
| `session_idle`              | Done                     |

When both an in-flight tool AND background tasks exist, show the
tool first; the background count moves to a separate badge.

**(c) Composer gating + background-task badge.** Composer textarea
+ Send button disabled while `!sessionIdle`. Below the composer
strip, when `bgTasks.size > 0`:

```
⏳ 2 background tasks running · Monitor (CI workflow), Monitor (CI Wave 1)
   Composer unlocks when they finish.
```

If only `inFlightToolUseIDs` is non-empty (no bg tasks), simpler
message: `Waiting for <toolName>…`.

## Data Flow Example

End-to-end for "monitor CI" scenario:

```
T0:    User sends prompt "push and monitor CI"
T0+0:  Backend: claude_handlers.go starts claude -p, runStates[sid] set
T0+1:  Lifecycle tracker: reset state for sid, resultSeen=false
T0+2:  PreToolUse hook fires for Bash(git push)
       Bridge → tool_intent{name:Bash} → tracker → WS tool_intent
       Frontend: create tool block with startedAt
T0+3:  PostToolUse hook for Bash → tool_done
T0+4:  PreToolUse hook for Monitor → tool_intent
T0+5:  PostToolUse for Monitor → tool_done (immediate; the bash polling is detached)
T0+6:  stream-json: result event arrives, resultSeen=true
       tracker: inFlight empty, BUT bg pending unknown yet (jsonl may lag)
       → does NOT emit session_idle yet
T0+7:  Jsonl tailer: queue-operation enqueue, task-id=bbk…, content starts with <task-notification>
       → bg_task_start frame, pendingBgTaskIDs[bbk…]={}
       (frontend: composer stays disabled, badge shows "1 bg task")
T0+15: Another task-notification enqueue → no-op (same task-id already pending)
…
T0+300: queue-operation remove, task-id=bbk…
       pendingBgTaskIDs empty, resultSeen=true → emit session_idle
       Frontend: composer unlocks, phase chip "Done"
```

The 6 → 7 race (`result` arrives before the first jsonl write for
the task-notification) is real. We handle it with a **grace period**:
on `result`, instead of immediately checking idleness, the tracker
waits up to **500 ms** for any jsonl event before emitting
`session_idle`. If a `bg_task_start` lands during that window,
session_idle waits for the corresponding `bg_task_end`. If nothing
lands, session_idle fires.

500 ms chosen because the jsonl tailer's fsnotify path (kernel →
inotify → goroutine → parse) is comfortably <100 ms in practice
on the Oracle pod; 5× headroom against bursty disk i/o.

## Error Handling

| Failure                                           | Behavior                                                                                                                |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| jsonl tailer fsnotify error / file disappears     | Log + emit `session_idle` immediately if `resultSeen`. Don't block forever waiting for events we can't observe.        |
| Hook script POST fails (bridge unreachable)       | Already handled — CLI denies the tool. No additional fallout; tracker just won't see tool_intent / tool_done.          |
| PostToolUse hook never fires (CLI bug / crash)   | Tool stays in `inFlightToolUseIDs`. Mitigation: when stream-json `tool_result` lands for that id, tracker also removes from map (belt-and-suspenders). |
| `result` event never arrives (`claude -p` crash)  | `claude_run_ended` (already exists) emits → tracker treats it as resultSeen=true and emits `session_idle` if otherwise quiescent. |
| Race: PostToolUse fires before PreToolUse         | Shouldn't happen per CLI contract. If it does: drop the orphan tool_done (no tool_intent to pair with).                |
| Backend restart mid-turn                          | jsonl tailer + run state lost. On restart, no in-flight tracking until next prompt — acceptable since `claude -p` child is also dead. |

## Testing

Each new component gets its own unit test file. Integration coverage
focuses on the four-event interleaving that the design hinges on.

- `internal/claude/jsonl_tailer_test.go` — fixtures of real jsonl
  snippets (committed under `testdata/`); assert correct
  classification of queue-operation entries vs user prompts vs
  task-notifications.
- `internal/api/lifecycle_test.go` — table-driven event sequences:
  - "result then bg start then bg end" → idle after bg end
  - "result with no bg" → idle within 500 ms grace
  - "bg start before result" → idle only after both
  - "PostToolUse without preceding Pre" → orphan dropped
- `internal/claude/bridge_test.go` — add cases for PostToolUse
  payload parsing + `tool_done` emission.
- `web/src/features/sessions/claudeReducer.test.ts` — new event
  cases (tool_intent, tool_done, bg_task_start, bg_task_end,
  session_idle). Existing tool_use_start cases assert no-op when
  block already exists.
- `web/src/features/sessions/sessionsReducer.test.ts` —
  composer-disabled derivation: `!sessionIdle && hasActiveTurn`.

E2E test (extend `web/e2e/`): full flow with a fake bridge POSTing
PreToolUse → Pre Monitor → PostToolUse Monitor → fake jsonl
appending task-notifications then a remove. Assert composer locked
until remove, then unlocked.

## Migration / Backwards Compatibility

This release does not change any existing WS frame's shape. Old
clients (cached HTML on a user's browser before the deploy) will
simply ignore the four new frame types and use the old
`inFlight` flag for composer gating — slightly worse UX but no
breakage. After they reload, the new gating kicks in.

The `tool_use_start` stream-json reducer's logic becomes "create
the tool block only if no block with this `toolUseId` exists yet."
During a live run, tool_intent will have arrived first and created
the block, so tool_use_start is a no-op. During history restore
(GET `/api/sessions/:id/claude-history`) there is no historic
tool_intent stream, so tool_use_start does the creation just like
today. Restored blocks have no `startedAt` — the elapsed timer
hides itself in that case (already handled by `useElapsed`
short-circuiting on undefined input).

## Rollout

Single PR. Merge to `next`, tag `v0.4`, deploy to Oracle as usual.
Behind no feature flag — the lifecycle tracker is always on, and
its only externally observable effect (composer gating) is strictly
an improvement over the v0.3 "spinner clears too early" behavior.

## Out of Scope (Future Work)

- **Subagent mini-chat** (v0.5): tail the `subagents/agent-*.jsonl`
  files and render the subagent's own tool_use list inline under
  its Agent block.
- **Per-tool stdout streaming** for Bash / Monitor in real time
  (v0.5 or later): would require intercepting the tool's process,
  not just observing pre/post hooks.
- **Background-task notification** when session_idle fires while
  user is on a different tab (browser Notification API): nice-to-have.
